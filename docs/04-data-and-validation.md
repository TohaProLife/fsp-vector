# 4. Данные и проверка качества

## 4.1. Главный принцип

Организатор не предоставляет кандидатские/вакансийные датасеты, API ФСП или gold labels. Собственная процедура оценки — часть конкурсного решения. Нужно показать, что проверяли, кто размечал, какая версия алгоритма оценивалась и что результаты позволяют заключить.

**Разделять три вида доказательств:** тесты программной корректности, модельные симуляции и наблюдения на людях. Большое число synthetic profiles не превращает симуляцию в исследование реального найма.

Все пороги этого документа — цели будущей проверки, не полученные результаты. В отчёте до запуска эксперимента используется `NOT_MEASURED`; числа не заполняются предположениями.

## 4.2. План собственных данных

| Набор | Целевой объём | Задача | Происхождение |
|---|---:|---|---|
| `demo-personas` | 30–50 подробных профилей | Понятная демонстрация всех состояний | Полностью вымышленные, вручную проверенные |
| `synthetic-candidates-v1` | 3 000 профилей | Load, фильтры, matching simulation | Генератор с seed, latent и observed слоями |
| `synthetic-needs-v1` | 150 потребностей | Разные направления, стек, условия | Вымышленные реалистичные описания, expert review |
| `synthetic-fsp-v1` | 300–600 событий/записей | Интеграция, отсутствие/отзыв/недоступность | Явный demo origin |
| `matching-gold-v1` | 60 потребностей × 20 кандидатов = 1 200 пар | Независимые relevance labels | Два разметчика, adjudication; blind к engine score |
| `need-extraction-gold-v1` | 150 описаний | Skills, negative/optional/required, цитаты | Отдельные авторы/разметчики от разработчика extractor |
| `resume-import-gold-v1` | 30–50 синтетических PDF | Точность импорта и отказ на проблемных файлах | Generated PDF/text/scans без реальных контактов |
| `assessment-reference-v1` | Все active families × ≥100 seeds | Корректность генератора/oracle | Независимый solver и property tests |
| `human-pilot-v1` | Цель 48–72 добровольца до сдачи при доступности | Время, понимание, формы, предварительная повторяемость | Согласие, минимизация данных, заявленный режим инструментов |
| `usability-v1` | ≥10 кандидатов + ≥5 работодателей/людей в роли HR | Полный путь без подсказок | Протокол задач, наблюдения и время |

Человеческий пилот такого размера не даёт полной калибровки всех 24 сочетаний специализации и грейда. Он должен концентрироваться на основных треках с достаточными наблюдениями, а не создавать видимость статистики по всему каталогу. По остальным указывается expert-initial статус. Более широкий пилот и эмпирическая IRT-калибровка — следующий этап.

В демонстрационном наборе обязательно есть сильный кандидат без ФСП, новичок, завысивший грейд, кандидат с насыщенным резюме и слабой проверкой, кандидат с честным кратким резюме и хорошей практикой, участник команды ФСП с неизвестной ролью, stale/revoked evidence, скрытый профиль и кандидат с несовместимыми условиями.

## 4.3. Схема данных и происхождение

Каждый dataset содержит `dataset_id`, version, generated/collected at, authors/labelers, seed, split policy, schema version, license/consent, SHA-256 и ограничения использования.

Слои кандидата в simulation:

- **Latent:** предполагаемые истинные specialization, competencies, способность, стиль решения.
- **Observed:** заявленное резюме, фактические имитированные ответы, noisy evidence и условия.
- **Gold:** relevance к конкретной потребности по независимой заранее описанной rubric.

Engine получает только observed projection. Создатель gold не читает score текущего engine. Даже такое разделение остаётся симуляцией и требует независимой человеческой проверки для содержательных выводов.

Пример assessment record:

```json
{
  "dataset_id": "pilot-v1",
  "participant_alias": "p-017",
  "specialization": "backend",
  "target_grade": "middle",
  "form_version": "backend-python-middle-v1",
  "task_family_version": "event-dedup-v2",
  "instrument_policy": "docs_allowed_ai_disallowed",
  "score": null,
  "expert_reference": null,
  "reference_kind": "NOT_MEASURED"
}
```

Контакты добровольцев хранятся отдельно, в public dataset только согласованные обезличенные/синтетические проекции. Исходные частные резюме и журналы попыток не попадают в открытый репозиторий.

## 4.4. Независимая разметка подбора

Единица — пара «потребность × профиль». Rubric:

| Label | Интерпретация |
|---|---|
| 0 | Не соответствует направлению/грейду либо критичным условиям |
| 1 | Частичное совпадение, большие неопределённости/пробелы |
| 2 | Подходит для первичного разговора с обозначенными ограничениями |
| 3 | Сильное соответствие по требуемым подтверждениям и условиям |

Разметчики оценивают факт приглашения к разговору, а не предсказывают успешный найм. ФСП можно учитывать как дополнительное свидетельство, но gold не должен повторять точную формулу `55/20/10/5/5/5`.

Порядок:

1. Утвердить rubric и 10 учебных примеров, не включаемых в test.
2. Разделить train/dev/test по потребностям, авторами написанных шаблонов и семействам кандидатов. Почти одинаковые тексты не размещать в разных split.
3. Два независимых эксперта размечают пары без engine score и названия алгоритма.
4. Измерить inter-rater agreement; расхождения разрешает третий участник/согласованная процедура.
5. Зафиксировать test hash до tuning.
6. Tune только на dev. Один финальный прогон на locked test.
7. Публиковать rubric, версии и все ограничения; после публикации test становится regression benchmark, а не новым независимым тестом следующей версии.

Если эксперт не доступен, метки называются team-labelled synthetic, а не экспертной разметкой рынка. Это допустимая ограниченная процедура, но её вес доказательства ниже.

## 4.5. Метрики matching

| Метрика | Зачем |
|---|---|
| Precision@5 / @10 | Доля кандидатов с label ≥2 в верхних позициях |
| nDCG@5 / @10 | Учитывает несколько уровней релевантности и порядок |
| Recall@10 / eligible recall | Проверяет потери подходящих людей, особенно от admission/retrieval |
| Candidate coverage | Кто вообще получает шанс попасть в выдачу |
| Gate violation rate | Попадание неправильной категории/отозванного профиля |
| Evidence contradiction rate | Объяснение утверждает навык, которого нет в допустимом evidence |
| Preference violation rate | Предложение нарушает явно заданное жёсткое условие кандидата |
| Empty-result quality | Понятность и корректность ответа при отсутствии кандидатов |

Для Precision@K заранее фиксируется знаменатель: K; недостающие позиции считаются нулевыми, отдельно сообщается размер допустимой базы. Для nDCG используется gain `2^label-1`; queries с IDCG=0 обрабатываются отдельно с явным числом исключений, а не улучшают среднее молча.

Нужны два вида оценки: внутри одинаково допущенного множества и end-to-end по всему gold population. Иначе строгий фильтр может исключить хороших кандидатов, а метрика на оставшихся это скроет. Retrieval recall измеряется отдельно от reranking.

Baselines: случайный порядок внутри категории; keywords/BM25 по резюме; keywords + заявленный грейд; подтверждённая категория + тест; полный engine. Для каждого один и тот же набор, запреты и метрики.

Ablations: без подтверждений, без ФСП, без semantic feature, без freshness, без must-have gate, без graph transfer. Улучшение FSP нельзя доказать, если генератор специально сделал FSP идеальным индикатором latent ability; требуется sensitivity к независимому/слабому/шумному FSP-сигналу.

Предварительные цели: Precision@5 ≥0,80; nDCG@10 ≥0,80; улучшение относительно сильного keyword baseline по nDCG не менее 0,05; gate violations =0. Это цели для собственного benchmark, не обещание качества реального рынка. Доверительные интервалы — bootstrap по queries, а не по зависимым парам.

## 4.6. Метрики тестирования

| Проверка | Метод и ограничение |
|---|---|
| Корректность экземпляра | Независимый solver по публичному условию; несовпадение с oracle блокирует family |
| Стабильность сложности форм | Сравнение состава, времени и результата на matched/counterbalanced пилоте |
| Test–retest | Parallel forms в разном порядке; agreement, weighted κ, correlation с интервалами |
| Discrimination | Item–rest correlation; доля решений по экспертным группам; интервалы |
| Соответствие экспертам | Confusion matrix, exact/within-one agreement, weighted κ, over/under-grading |
| Практическая валидность | Соответствие задаче роли, отдельная оценка типичных рабочих действий |
| Ограничения времени | Median/p90 завершения, missing items, dropout, технические failures |
| Справедливость форм | Проверка сравнимых групп/условий при достаточном размере; малые группы явно отмечены |

Вместо зависимости от одной общей accuracy обязательно показывать **over-grading**: ошибка, при которой подтверждённый уровень выше независимого экспертного ориентира. Опыт работы или самооценка не становятся единственной «истиной» о грейде.

Цели для пилота: majority-form agreement ≥85% и weighted κ ориентировочно ≥0,70; время p90 в заявленном лимите; 100% active generator variants проходят independent correctness checks. Небольшой pilot может не дать точной оценки: публикуется фактический интервал и ограничения, не искусственный PASS по округлённому числу.

## 4.7. Эксперимент с распространением заданий

Нужно сравнить четыре подхода: фиксированный тест, A/B-банк, параметрические формы и формы с контрольной мутацией. Один набор skill levels и общий режим инструментов.

Атакующие условия:

1. Нет знакомства с задачей.
2. Известен старый точный answer key.
3. Известно условие и полное решение прошлого варианта.
4. Известен шаблон/алгоритм решения семейства.
5. Известны несколько семейств и доступны обычные developer tools.
6. Доступна LLM на новых вариантах — отдельный эксперимент в таком режиме.

Мерить pass-rate inflation, перенос правильного ответа, изменение времени и успех на контрольной мутации. Сравнение «ответ известен только для старого ID, а все новые ID честно решаются по вероятностной модели» проверяет лишь узкий случай и не доказывает античит.

Цель по прямому переносу старого ответа — заметно меньший прирост pass rate, чем на фиксированном тесте, с confidence interval. Для передачи метода решения результат может быть высоким: освоенный метод частично и является проверяемым навыком. Нельзя считать любое обучение семейства мошенничеством.

Эксперимент с LLM показывает ограничения режима. Параметризация и мутация не могут гарантировать, что удалённый помощник не решит всё. Это отражается в итоговом evidence и будущей policy.

## 4.8. NLP и импорт PDF

Измерять field-level precision/recall для specialization, grade, skill, required/preferred/negated, salary, work format и source spans. Важнее не извлекать отрицательное требование как must-have, чем распознать лишнее ключевое слово.

Набор включает смешанный RU/EN, аббревиатуры, отрицания, optional, неоднозначный грейд, валюту, пустые поля, длинный текст и malicious prompt-like фразы. Text воспринимается как данные; он не может менять system policy или действия сервера.

PDF cases: текстовый PDF, колонки, плохая кодировка, скан без OCR, password-protected, oversized, неверный MIME. При невозможности разбора предложить ручную форму. Скан без установленного OCR не должен завершаться фиктивным «распознано».

Extractor goals: precision обязательных/исключённых условий ≥0,90 на locked team benchmark и показ цитаты для каждого подтверждаемого поля. Человек всё равно подтверждает draft. Это не автоматическое доказательство professional competency.

## 4.9. Пользовательское тестирование

Задания кандидату: регистрация/email → профиль → опрос → старт/восстановление теста → понимание результата → публикация → принятие/отказ → отзыв contacts. Отдельный участник проходит путь без ФСП.

Задания работодателю: компания → потребность → подтверждение extracted requirements → подборка → фильтры/возврат → сравнение → приглашение без вакансии → прочитать статус → открыть контакты только после принятия.

Записывать task completion, время, неверные переходы, обращения за помощью и понимание salary/evidence. Цель: ≥90% успешно завершают основные задачи без подсказок; при малом N приводить абсолютные числа, а не только процент.

Доказать снижение времени найма за несколько дней нельзя. Можно измерить время до **релевантного приглашения** в контролируемом сценарии и сравнить с baseline flow. Принятие приглашения — не трудоустройство.

## 4.10. Безопасность, отказоустойчивость и нагрузка

Критические негативные проверки:

- Кандидат не читает другого кандидата, попытку, приглашение или contacts.
- Работодатель не читает чужую потребность, invitation, grant или ATS connection.
- Контакты скрыты до acceptance во всех проекциях, PDF, SSR, export и saved runs.
- Acceptance конкретной компании не открывает доступ другой; отзыв немедленно закрывает новый запрос.
- Невалидная зарплата, повтор send/submit, concurrent accept/withdraw и изменённая terms version обработаны.
- Неподтверждённый email, истёкшая session, CSRF и неверный OIDC callback отклонены.
- Нет arbitrary FSP linking, identity mismatch и cross-user source data.
- Runner network, mounts, fork bomb, бесконечный цикл, память и stdout ограничены.
- Падение worker после бизнес-фиксации не теряет событие; restart не создаёт дубли.
- FSP/ML/SMTP outage не превращается в ложный success.

Нагрузочный профиль: 50 одновременных пользователей, 3 000 candidates, 150 needs; отдельная очередь judge с ограниченной concurrency. Цели: обычный API p95 ≤500 ms, search/profile p95 ≤1 s, новый match run p95 ≤2 s без online LLM. Judge latency измеряется отдельно и показывает очередь. Эти пределы уточняются на конкретном локальном hardware, который указывается в отчёте.

Ресурсный отчёт содержит CPU, RAM, OS/WSL, Docker versions, размер данных, warm/cold model state, длительность и ошибки. Readiness после fresh start проверяется отдельно от прогретого load run.

## 4.11. Финальный формат отчётов

Содержимое каждого experiment report:

1. Research question и ожидаемая проверка.
2. Dataset hash, версии и provenance.
3. Rubric/split/labeling protocol.
4. Baseline и модель/algorithm version.
5. Команда воспроизведения, seed, commit, environment.
6. Результаты, интервалы, absolute counts и failure cases.
7. Разбор ошибок, ablation и ограничения.
8. Решение: release, исправление или исключение неподтверждённого свойства.

`evaluate` выдаёт JSON + Markdown и сохраняет run manifest. Финальная сопроводительная документация собирается в DOC/PDF с фактическими результатами, графиками confusion matrix, form variance, ranking gains и latency. Графики не строятся из выдуманных значений.
